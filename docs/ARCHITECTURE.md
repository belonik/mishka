# Архитектура Mishka

Документ описывает, как устроено приложение, почему приняты ключевые решения и какие
места требуют осторожности при доработке. Предполагается знакомство с Swift, SwiftUI и AppKit.

---

## 1. Общая картина

Приложение — одно окно, три колонки, один источник истины для данных. Никаких внешних
зависимостей: только системные фреймворки.

```
┌──────────────────────────────────────────────────────────────────────┐
│  MishkaApp (SwiftUI App, сцена Window)                               │
│  ├── AppDelegate      приём файлов из Finder, запись индекса на выходе│
│  └── MishkaCommands   меню, горячие клавиши                           │
└──────────────────────────────────────────────────────────────────────┘
                    │ environmentObject
                    ▼
┌──────────────────────────────────────────────────────────────────────┐
│  AppState  ──  единый наблюдаемый фасад для всех представлений        │
│  │  выбор раздела, поиск, сортировка, история файлов, уведомления     │
│  └── ретранслирует objectWillChange из NoteStore ──────────┐          │
└───────────────────────────────────────────────────────────┼──────────┘
                    │                                        │
                    ▼                                        ▼
        ┌───────────────────────┐              ┌──────────────────────────┐
        │  RootView             │              │  NoteStore               │
        │  ├── SidebarView      │              │  ├── notes / trash / index│
        │  ├── NoteListView     │              │  ├── открытие внешних файлов│
        │  └── EditorPane       │              │  ├── фильтрация и поиск   │
        │      ├── MarkdownEditor (AppKit)     │  └── сериализация на диск │
        │      └── MarkdownPreviewView (WebKit)└──────────────────────────┘
        └───────────────────────┘
                    │
                    ▼
        ┌───────────────────────┐   ┌────────────────────┐
        │ MarkdownHighlighter   │   │ MarkdownRenderer   │
        │ атрибуты для NSText…  │   │ Markdown → HTML+CSS│
        └───────────────────────┘   └────────────────────┘
```

Слои и их зависимости строго направлены: представления знают о состоянии, состояние — о
хранилище, хранилище не знает ни о чём, кроме Foundation. Подсветка и рендерер — чистые
функции над текстом и темой, они не зависят от состояния.

## 3. Модель данных

### 3.1. `Note`

```swift
struct Note: Identifiable, Hashable, Codable {
    var id: UUID
    var text: String                  // весь Markdown, включая строку заголовка
    var createdAt: Date
    var modifiedAt: Date
    var isPinned: Bool
    var isLocked: Bool
    var isTrashed: Bool
    var trashedAt: Date?
    var externalPath: String?         // nil → заметка хранится в vault
    var isMissing: Bool               // привязанный файл недоступен

    // производные, пересчитываются в refreshDerived()
    var title: String
    var snippet: String
    var tags: [String]
    var hasOpenTask: Bool
}
```

**Почему заголовок не хранится отдельно.** В Bear заголовок — это первая строка заметки.
Такое решение убирает рассинхронизацию: файл остаётся чистым Markdown, а заголовок всегда
соответствует содержимому. Производные поля кэшируются в структуре, чтобы список из тысячи
строк не пересчитывал разбор тегов на каждой перерисовке.

**Что не хранится.** Всё, что можно вывести: заголовок, сниппет, теги, наличие открытых
задач. Всё, что вывести нельзя, живёт в индексе.

### 3.2. Индекс

```swift
struct NoteRecord: Codable {           // запись в library.json
    var id: UUID
    var createdAt, modifiedAt: Date
    var isPinned, isLocked, isTrashed: Bool
    var trashedAt: Date?
    var externalPath: String?
}

struct LibraryIndex: Codable {
    var version = 1
    var records: [NoteRecord]
    var selectedNoteID: UUID?
}
```

Индекс — вторичен. Загрузка (`NoteStore.load()`) работает по правилу «файлы главнее»:

1. Читается индекс (при неудаче — пустой).
2. Сканируются `notes/` и `trash/`; для каждого файла создаётся заметка, к ней применяются
   метаданные из индекса, если запись есть.
3. Дозагружаются внешние файлы из записей с `externalPath`; отсутствующие помечаются
   `isMissing`, но запись сохраняется.
4. Выбирается заметка для открытия, при этом удалённая в корзину не выбирается никогда.
5. Индекс перезаписывается по фактическому состоянию.

Если `library.json` удалить, шаг 1 даст пустой индекс, шаг 2 восстановит все заметки,
а датами станут даты файлов. Пользователь потеряет только закрепление и корзину.

### 3.3. Дерево тегов

`TagNode.build(from:)` строит дерево за один проход: для каждого тега создаются все
промежуточные узлы (`работа/проекты/сайт` → `работа`, `работа/проекты`, `работа/проекты/сайт`),
а счётчик родителя суммирует счётчики потомков. Это позволяет сворачивать узел и всё равно
видеть, сколько заметок внутри.

Результат кэшируется в `NoteStore` и сбрасывается в `didSet` свойства `notes`, чтобы за один
проход отрисовки дерево не строилось дважды (сайдбар обращается к нему и в условии, и в теле).

## 4. Хранилище

### 4.1. Пути

```
<root>/notes/<uuid>.md      активные заметки
<root>/trash/<uuid>.md      корзина
<root>/library.json         индекс
```

`<root>` — `~/Library/Application Support/Mishka`, если не задан `--vault <path>` или
переменная `MISHKA_VAULT`.

### 4.2. Запись

Все операции ввода-вывода идут через последовательную очередь `ioQueue`:

- обычные заметки — `String.write(to:atomically: true)`;
- внешние файлы — `NoteStore.writeExternal`: путь разрешается от симлинков, запись
  атомарная, после неё возвращаются исходные POSIX-права (атомарная замена меняет inode,
  и без этого файл в git-репозитории потерял бы права).

Индекс сохраняется с задержкой 0,8 с (`Debouncer`), чтобы набор текста не порождал запись
на каждое нажатие. На выходе из приложения `AppDelegate.applicationWillTerminate` вызывает
`NoteStore.flush()`, который досрочно применяет отложенную запись и дожидается опустошения
очереди.

### 4.3. Внешние файлы

Ключевое требование — **не копировать и не портить чужой файл**. Отсюда:

| Решение | Причина |
| --- | --- |
| Идентификатор заметки не выводится из пути | Файл можно переместить; запись ищется по `externalPath`, а не по имени |
| Повторное открытие того же пути переиспользует запись | Иначе история заполнялась бы дубликатами |
| Файл из хранилища, открытый напрямую, не создаёт вторую запись | Сравниваются разрешённые пути |
| `moveToTrash` для внешней заметки вызывает `forget` | Приложение не владеет файлом и не вправе его перемещать |
| `deletePermanently` и `emptyTrash` пропускают внешние заметки | Защита от потери данных пользователя |
| Пропавший файл остаётся в списке с `isMissing` | Иначе история терялась бы при отключении диска |
| `refreshExternalNotes()` вызывается при активации приложения | Подхватывает правки из других редакторов |

## 5. Редактор

### 5.1. Стек TextKit собирается вручную

```swift
let storage = NSTextStorage()
let layoutManager = MarkdownLayoutManager()
storage.addLayoutManager(layoutManager)
let container = NSTextContainer(...)
layoutManager.addTextContainer(container)
let textView = MarkdownTextView(frame: .zero, textContainer: container)
```

Причина — **TextKit 1, а не TextKit 2**. Чекбоксы, маркеры списков и карточки таблиц
рисуются в `drawBackground(forGlyphRange:at:)`, то есть под текстом, в левом отступе и
вокруг абзацев. TextKit 2 не даёт такого доступа к геометрии строк. Побочный эффект:
`NSTextView` приходится создавать с явным контейнером, иначе система выберет TextKit 2.

### 5.2. Подсветка как раскраска атрибутов

`MarkdownHighlighter.highlight(_:selection:)` **никогда не меняет символы**. Он только
раскладывает атрибуты поверх существующего текста, поэтому в файле всегда ровно то, что
набрал пользователь, а отмена и повтор работают штатными средствами `NSTextView`.

Порядок проходов важен:

```
1. setAttributes(baseAttributes)              сброс всего, базовый шрифт и цвет
2. scanStructure                              построчно: блоки кода, заголовки, цитаты,
                                              списки, задачи, таблицы, front matter
3. scanInline                                 регулярками: код, ссылки, URL, викиссылки,
                                              теги, затем эмфаза от широких маркеров к узким
```

Проход 3 пропускает всё, что попало в `protected` на предыдущих шагах. Благодаря этому
`**звёздочки**` внутри блока кода и внутри ссылки не превращаются в жирный шрифт.

### 5.3. Сокрытие маркеров

Символы разметки (`**`, `#`, `` ` ``, `](url)`) не удаляются, а **сжимаются**: назначается
шрифт размером 0,1 pt и прозрачный цвет. Глифы занимают доли точки и визуально исчезают,
но позиции символов и каретка остаются корректными.

Показывать или скрывать — решает абзац с курсором. `revealParagraph` вычисляется один раз
в начале подсветки; маркер виден, если пересекается с этим абзацем. При перемещении каретки
внутри одного абзаца переподсветка не запускается вообще — сравнение в
`setSelectedRange(_:affinity:stillSelecting:)` отсекает лишнюю работу.

### 5.4. Гуттер

Пользовательские атрибуты — это канал связи между подсветкой и отрисовкой:

| Атрибут | Значение | Кто читает |
| --- | --- | --- |
| `.mishkaTask` | 1 — выполнено, 0 — открыто | `drawListGutters` рисует чекбокс |
| `.mishkaBullet` | уровень вложенности | `drawListGutters` рисует кружок |
| `.mishkaIndent` | уровень абзаца | геометрия гуттера и карточек |
| `.mishkaMarker` | 1 — скрыт, 0 — показан | диагностика |
| `.mishkaTableRole` | 0 шапка, 1 разделитель, 2 тело | `drawTables` |
| `.mishkaTableBlock` | `NSValue(range:)` всей таблицы | `drawTables` группирует строки |
| `.mishkaTableLast` | 1 на последней строке | последняя строка без разделителя |

Щелчок по чекбоксу обрабатывается в `mouseDown`: точка переводится в координаты контейнера,
ищется символ, читается `.mishkaTask`, проверяется попадание в левый отступ — и только тогда
`[ ]` меняется на `[x]` через `shouldChangeText`/`replaceCharacters`, то есть с записью в стек отмены.

### 5.5. Таблицы в редакторе

Таблица распознаётся, только если строка содержит `|` **и** следующая за ней строка является
разделителем (`|---|:---:|`). Это защищает от ложных срабатываний на обычном тексте с
вертикальной чертой.

Отрисовка карточки (`MarkdownLayoutManager.drawTable`):

1. Собираются прямоугольники всех строк таблицы.
2. `contentMaxX` берётся из `lineFragmentUsedRect` — это фактическая ширина самой длинной
   строки, поэтому карточка обнимает содержимое, а не растягивается на всю колонку.
3. Рисуется скруглённый прямоугольник, подложка и рамка.
4. Под шапкой и между строками тела рисуются разделители.

Строка-разделитель сворачивается: `minimumLineHeight = maximumLineHeight = 5`. Если курсор
попадает на неё, высота возвращается к обычной и текст становится видимым — так её можно
отредактировать.

### 5.6. Поведение ввода

| Действие | Реализация |
| --- | --- |
| `Enter` в списке | `insertNewline` строит продолжение маркера; на пустом пункте удаляет маркер |
| `Tab` / `⇧Tab` | `insertTab`/`insertBacktab` сдвигают абзац на два пробела |
| `⌘B`, `⌘I`, `⌘⇧X`, `⌘⇧H`, `⌘⇧C` | `wrapSelection` — оборачивает или разворачивает выделение |
| `⌘1…⌘3`, `⌘0` | `setHeadingLevel` заменяет префикс заголовка |
| `⌘⇧L`, `⌘⇧8`, `⌘⇧9`, `⌘'` | `toggleLinePrefix` на все строки выделения |
| `⌘K` | `wrapSelectionAsLink` подставляет `[текст](url)` и выделяет `url` |

Все команды формата вызываются из меню через `NSApp.sendAction(_:to: nil)` — то есть идут по
цепочке респондеров и попадают в первое поле ввода, без прямой связи между меню и редактором.

## 6. Превью

### 6.1. Разделение документа и содержимого

`MarkdownRenderer` собирает полный HTML со встроенной таблицей стилей. Стили зависят только
от темы и шрифта, содержимое — только от текста. Поэтому:

- **смена темы или гарнитуры** → полная перезагрузка документа (`loadHTMLString`);
- **любое изменение текста** → подмена `document.body.innerHTML` через `evaluateJavaScript`.

Второй путь не трогает прокрутку читателя, поэтому в режиме «пополам» можно печатать и не
терять место чтения.

### 6.2. Гонка загрузки — главная тонкость

`loadHTMLString` асинхронна. Если переключить заметку, пока документ ещё грузится,
обновление содержимого применится к странице, а затем завершившаяся загрузка **затрёт его** —
превью отстанет на одну заметку навсегда, потому что нового события уже не будет.

Решение — очередь:

```swift
if loadedSignature != signature {        // тема/шрифт изменились
    renderedMarkdown = markdown
    webView.loadHTMLString(document, …)  // полная перезагрузка
    return
}
guard renderedMarkdown != markdown else { return }
guard isReady else {
    pendingMarkdown = markdown           // загрузка в полёте — придержать
    return
}
apply(markdown)                          // подмена innerHTML
```

`didFinish` применяет `pendingMarkdown`, и только там это безопасно. `didStartProvisionalNavigation`
сбрасывает `isReady`, чтобы состояние не рассинхронизировалось.

### 6.3. Санитизация

Ссылки фильтруются на этапе рендера: схемы `javascript:`, `data:`, `vbscript:` не попадают
в `href`, остаётся обычный текст. Относительные пути к изображениям переписываются в
`file://` относительно каталога заметки, который передаётся как `basePath`.

## 7. Состояние и наблюдаемость

### 7.1. Два объекта, один фасад

```
NoteStore (данные)  ──objectWillChange──▶  AppState (интерфейс)  ──▶  SwiftUI
```

Все представления подписаны на `AppState` через `@EnvironmentObject`, а на `NoteStore` —
никто. Поэтому в `AppState.init` стоит ретрансляция:

```swift
storeSubscription = store.objectWillChange.sink { [weak self] in
    self?.objectWillChange.send()
}
```

**Это неочевидное, но критичное место.** Без него клик по заметке меняет модель, но SwiftUI
не перерисовывается — интерфейс выглядит «мёртвым». Ошибка коварна тем, что часть действий
всё равно обновляла экран: они попутно меняли `@Published` свойства `AppState` (например,
показ уведомления), и перерисовка происходила как побочный эффект. Регрессионный тест
`Tests/Subscriptions` проверяет каждую операцию хранилища.

### 7.2. Идентичность представлений AppKit

Панели редактора и превью помечены `.id("mishka-editor")` / `.id("mishka-preview")`.
Без явной идентичности SwiftUI пересоздавал `WKWebView` по нескольку раз за перерисовку,
что давало лишние загрузки и мерцание. Сейчас на всю сессию создаётся одно превью.

### 7.3. Одно окно

Сцена — `Window`, а не `WindowGroup`. `WindowGroup` создаёт новое окно на каждое
«открыть с помощью» из Finder; в отладке такой сценарий дал семь окон и семь экземпляров
`WKWebView`.

## 8. Темы

`Theme` — плоская структура из 17 цветов в формате `#RRGGBB`, `Codable` и `Hashable`.
Плоскость выбрана сознательно: палитра целиком сериализуется, сравнивается и передаётся в
CSS без преобразований. `ThemeCatalog` содержит 16 тем (6 светлых, 10 тёмных), `AccentCatalog` —
12 акцентов, независимых от темы.

Контраст проверен численно, худшее значение — 5,59:1 (Solarized Light), что выше требований
WCAG AA. Канонические палитры Solarized в двух местах сознательно отклоняются от оригинала:
иначе контраст не дотягивал до AA.

Один и тот же объект `Theme` питает и AppKit (`NSColor(hex:)`), и CSS
(`MDRStylesheet.build`). Это единственная гарантия того, что редактор и превью выглядят
согласованно.

## 9. Сборка

`build.sh` не использует Xcode-проект: SwiftPM собирает исполняемый файл, а скрипт
достраивает вокруг него `.app`-бандл.

```
swift build -c release
→ .build/release/Mishka
→ dist/Mishka.app/Contents/MacOS/Mishka
→ dist/Mishka.app/Contents/Info.plist      (генерируется скриптом)
→ dist/Mishka.app/Contents/Resources/AppIcon.icns  (рисуется Tools/make-icon.swift)
→ codesign --force --deep --sign -          (ad-hoc подпись)
```

`Package.swift` объявляет один исполняемый таргет с `swiftLanguageMode(.v5)`: язык Swift 6
включил бы строгую проверку изоляции, которая конфликтует с AppKit-кодом, работающим на
главном потоке без аннотаций.

## 10. Ключевые решения

| № | Решение | Альтернатива | Почему так |
| --- | --- | --- | --- |
| 1 | Текст хранится как чистый `.md`, метаданные отдельно | YAML-front-matter внутри файла | Файл остаётся читаемым и не засоряется; front matter уже встречается у пользователя и трактуется как данные |
| 2 | TextKit 1 со своим layout-менеджером | SwiftUI `TextEditor`, TextKit 2 | Нужна отрисовка в гуттере и под текстом; SwiftUI этого не даёт |
| 3 | Подсветка — только атрибуты, без правки строки | Собственный `NSTextStorage` с перезаписью | Гарантирует, что в файл попадает ровно набранный текст, и сохраняет штатную отмену |
| 4 | `AppState` как единственный наблюдаемый фасад | Подписка каждого представления на `NoteStore` | Меньше связей и одно место, где объясняется ретрансляция |
| 5 | Одно окно (`Window`) | `WindowGroup` | Иначе каждое открытие файла из Finder плодит окно |
| 6 | Индекс вторичен, файлы первичны | SQLite как источник истины | Данные пользователя не запираются в базе; индекс пересобирается |
| 7 | Внешние файлы не копируются | Импорт с копированием | Требование работать в git-репозиториях; копия создаётся только по явной команде |
| 8 | Нет App Sandbox | Песочница | Правка файлов в произвольных каталогах несовместима с ней |
| 9 | Плоская структура темы | Вложенные группы цветов | Тема целиком уходит в CSS и сравнивается как одно значение |
| 10 | Тесты — отдельные исполняемые программы | XCTest | Таргет исполняемый, тестовый бандл не может его импортировать |

## 11. Подводные камни

Собраны по ходу разработки; каждый стоил отладки.

1. **SwiftPM и кэш модулей.** В ограниченном окружении драйвер не может писать в
   `/var/folders/.../ModuleCache`. Лечится `CLANG_MODULE_CACHE_PATH` — переменная уже
   выставляется в `build.sh` и `Tests/run-tests.sh`.
2. **`border-radius` и скролл-контейнер.** WebKit не срезает скруглённые углы у элемента
   с `overflow-x: auto`. Карточка таблицы поэтому построена из двух блоков: внешний
   прокручивает, внутренний со `overflow: hidden` рисует скруглённую рамку.
3. **Гонка `loadHTMLString`.** Описана в разделе 6.2; лечится очередью `pendingMarkdown`.
4. **Отсутствие ретрансляции `objectWillChange`.** Описана в 7.1; ловится тестом.
5. **`WindowGroup` и файлы из Finder.** Каждое «открыть с помощью» создавало окно.
6. **Асинхронные записи в тестах.** `NoteStore.flush()` нужно вызывать до чтения файла с
   диска, иначе тест увидит старое содержимое.
7. **Синтез событий мыши недоступен.** `CGPreflightPostEventAccess()` возвращает `false`,
   поэтому клики мышью в проверках автоматизировать нельзя — эти пункты приёмки помечены
   как проверяемые вручную.
8. **Первая строка — не всегда заголовок.** Файлы с YAML-шапкой давали заголовок `---`,
   пока не появилось распознавание front matter.

## 12. Что дальше

Технический долг и напрашивающиеся доработки, в порядке убывания ценности:

1. **Конфликты внешних правок.** Сейчас побеждает последняя запись. Нужны отслеживание
   версии файла и диалог слияния.
2. **Наблюдение за файлами.** `refreshExternalNotes()` срабатывает при активации;
   `DispatchSource` на каталог дал бы реакцию в реальном времени.
3. **Выравнивание колонок таблиц при наборе.** Дополнение пробелами по нажатию `Tab`.
4. **Переход по `[[викиссылкам]]`.** Сейчас они только подсвечиваются.
5. **Форматирование в строке списка.** Прогресс задач, превью картинок.
6. **VoiceOver.** Строки списка доступны, но редактор требует отдельных усилий.
